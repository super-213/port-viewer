# Port Viewer 端口诊断深化计划

日期：2026-11-05。更新于 2026-11-06。本轮已确定先实施端口事件时间线、局部拓扑和 Docker 状态，实施范围与验证情况见第 10 节。其余章节保留后续规划。

## 1. 产品定位与目标

**围绕本机端口，准确解释服务归属、访问范围和状态变化，并帮助用户安全处理问题。**

面向 Mac mini 本地服务器和开发机场景深化能力，同时保持通用 macOS 端口工具的定位。安全提示、Docker 状态和 Cloudflare Tunnel 都作为端口诊断的上下文，不各自发展为独立平台。

本轮优先回答三个问题：

1. 这个端口是否按我的预期开放？
2. 这个端口最近发生了什么？
3. 这个端口背后的容器是什么状态？

本计划承接 [产品需求文档](PLAN-000-requirements.md) 的“系统工具”定位，补充当前代码基础上的后续范围，不追溯修改原文档的首版优先级。Cloudflare 的发现、证据绑定和兼容边界继续遵循 [Cloudflare Tunnel 联动计划](PLAN-004-cloudflare-tunnel-integration-plan.md)。

## 2. 当前基础

以下基于制定计划时的工作区代码；其中 Cloudflare 相关代码包含尚未提交的变更，不代表已发布能力。

| 已有基础 | 代码位置 | 本轮如何复用 |
|---|---|---|
| 原生端口采集、lsof 回退与操作前 fresh 校验 | `PortQueryService`、`DarwinPortService`、`LsofService` | 继续提供共享快照，不另建高频采集循环 |
| 进程启动身份、项目与服务归属 | `ProcessContext`、`ProcessContextResolver` | 区分进程实例与长期关注的服务，降低 PID 复用导致的错误关联 |
| Docker/Homebrew 识别与安全停止 | `ManagedServiceController` | 在明确容器归属上补充只读状态 |
| 监听访问范围解释 | `NetworkAccessScope` | 扩充可观察事实与用户预期之间的比较 |
| 最近 30 分钟会话内趋势 | `PortViewModel.activityHistory` | 保留数量趋势，另补可解释的端口事件 |
| Cloudflare 本地发现与状态展示 | `CloudflareTunnelService`、`TunnelSnapshot` | 将域名映射作为独立访问路径证据 |
| 列表、详情、局部拓扑与菜单栏 | 现有 View 和页面 ViewModel | 在现有入口呈现结果，避免增加多个监控工作台 |

当前趋势保存的是聚合采样点，不能直接当作占用者变更记录或完整历史回放。当前 Docker 解析主要覆盖运行容器和发布端口，补充停止、重启及健康信息需要扩展采集，不能仅增加展示字段。

## 3. 功能取舍

| 候选功能 | 结论 | 范围与理由 |
|---|---|---|
| 端口暴露风险检查 | 本轮优先 | 实现预期访问范围和偏差提示，不宣称漏洞检测或已验证公网暴露 |
| 敏感进程白名单 | 改造后纳入 | 改为服务、端点的预期策略，不按进程名称全局免检 |
| 历史回溯 | 本轮优先 | 最近 30 分钟的端口事件时间线，不建设全量快照录像 |
| Docker 健康度关联 | 本轮纳入精简版 | 归属、生命周期、已有健康检查与观察到的重启变化 |
| 连接数趋势 | 深化已有能力 | 支持查看具体服务的采样变化，不凭激增直接判定攻击 |
| 网络拓扑 | 深化局部关系 | 围绕选中端口展示有证据的映射和连接，不推测全局依赖图 |
| 延迟监测 | 后续候选 | 用户主动执行 TCP 连接测试，不把建连耗时称为既有连接 RTT 或应用响应时间 |
| 异常外连告警 | 暂缓 | 可先保留连接筛选和变化信息；自动判恶意需要处理基线、误报及采样缺失 |
| Geo-IP | 低优先级 | 仅作可选背景信息，地理位置不作为默认危险判据 |
| 每 PID 带宽、带宽 Top 5 | 暂缓 | 当前模型无字节计数，需要单独验证采集来源、覆盖率和归属准确性 |
| Docker CPU/内存 | 后续按需补充 | 只在对应端口详情按需读取，不建立资源监控面板 |
| 自动重启建议 | 暂缓 | 先呈现事实；连接波动、CPU 高或健康检查失败均不自动推导应重启 |
| JSON/YAML 规则与脚本执行 | 当前不纳入 | 使用有限内置监测条件，避免扩展规则语言和自动化执行环境 |
| K8s 深度集成 | 当前不纳入 | 避免引入集群、Pod、Service、命名空间及远程凭据管理 |
| 僵尸进程／孤儿端口清理 | 不按原方案实现 | 可解释持续异常状态；不提供误导性的 TCP 状态一键清理 |
| 温度、风扇联动 | 不纳入 | 与具体端口问题关联较弱，属于系统硬件监控 |
| 外接网卡识别 | 低优先级 | 有可靠证据时可显示接口，不扩展为硬件和物理链路诊断 |

非 80/443、海外地址、陌生地址都不足以证明恶意外连。TIME_WAIT 是正常 TCP 关闭阶段，CLOSE_WAIT 表示等待本地应用关闭连接，均不能直接等同于僵尸进程。相关依据见 [TCP 标准 RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)。

## 4. 优先能力一：预期访问范围与偏差提示

### 4.1 用户体验

在端口详情中提供“关注此服务”和“设置预期访问范围”。第一版限定为清晰的内置条件：

- **本机直接访问**：预期仅绑定回环地址。
- **允许局域网访问**：允许绑定具体局域网地址或通配地址，同时保留实际绑定说明。
- **允许指定 Tunnel 映射**：独立配置允许关联的域名，可与上述直接监听范围组合。

示例：

> Redis 的监听地址从 `127.0.0.1:6379` 变为 `0.0.0.0:6379`，超出了你设置的“本机直接访问”范围。

“仅回环监听”和“是否存在 Tunnel 映射”是两个维度。存在 Tunnel 映射时，不能因为绑定回环地址就宣称只能本机访问；连接器就绪也不等于公网端到端可用。

### 4.2 判断边界

- 覆盖 IPv4、IPv6、通配地址和具体接口地址；不能只检查 `0.0.0.0`。
- 通配监听只说明绑定范围，不证明互联网可以访问。允许局域网访问也不构成“禁止公网”的防火墙策略保证。
- TCP 第一版以 LISTEN 记录为判断对象。UDP 保留已有展示，后续另行定义绑定语义，不将其误标为 TCP 监听。
- 未配置预期的新服务默认给出信息提示，不触发高优先级安全告警。
- 只有明确违反用户预期且证据足够时才生成偏差；查询不完整、身份不足或 Tunnel 信息过期时显示“暂无法判断”，不显示为已恢复正常。
- 端口号可以用于说明“常见用途”，不能单凭 `6379` 或 `5432` 就认定服务类型。

### 4.3 策略身份与告警

长期策略不绑定 PID，也不按进程名永久信任。策略保存明确的目标信息：项目目录或可执行路径、协议及端口；Docker 使用已确认的本地端点和完整容器 ID。运行时事件另用进程启动身份或容器启动代次区分实例。

路径和项目归属用于匹配用户关注目标，不作为程序可信或未被篡改的安全证明。容器重建后 ID 改变，第一版要求用户重新关联，不按同名容器静默继承策略。

同一持续偏差只维持一项活动提示，避免每次刷新重复通知。恢复、再次发生、身份变化分别处理。默认先使用详情与菜单栏摘要；系统通知可由用户为关注目标开启。提示同时有图标和文字，不仅依赖红色。

### 4.4 验收标准

1. 回环绑定变为通配或具体非回环绑定时，能识别与用户预期的偏差。
2. IPv4/IPv6 结果完整展示；同一服务有多个监听端点时，不仅检查代表记录。
3. 回环监听但存在已确认 Tunnel 映射时，分别说明直接访问与转发路径。
4. 部分快照、身份变化和过期关联不产生虚假的风险恢复或重复告警。
5. 删除关注或修改预期后，派生提示及时更新；不执行任何系统配置修改。

## 5. 优先能力二：端口事件时间线

### 5.1 记录范围

记录应用运行期间最近 30 分钟的关键观察结果，第一版不跨退出持久化，不记录每条短连接，不保存完整命令行或全部原始快照。

| 事件 | 展示语义 |
|---|---|
| 新观察到监听 | 首次观察到某进程实例监听某端点 |
| 不再观察到监听 | 后续完整采样中未再观察到原监听 |
| 占用者变化 | 同一协议、地址及端口观察到不同占用实例；保留原先和当前占用者集合 |
| 监听范围变化 | 已确认同一目标的监听地址集合变化 |
| 容器实例变化 | 已跟踪容器的启动代次变化，关联相应端口 |
| Tunnel 映射变化 | 同一已确认关联的域名或目标发生变化 |
| 采样中断 | 查询失败、部分结果、暂停、休眠或其他无法连续比较的区间 |

示例：

```text
14:02  首次观察到项目 A 监听 :3000
14:07  不再观察到项目 A 监听 :3000
14:07  观察到项目 B 监听 :3000
14:09  项目 B 的监听地址从回环变为通配地址
```

### 5.2 正确性约束

- 时间表示采样观察时间，不承诺真实系统事件的精确发生时间；刷新间隔内的短暂变化可能遗漏。
- 首次完整采样建立基线，不把现有全部服务写成“刚启动”。
- 不使用 PID 单独判断同一进程；文件描述符变化不应制造虚假的服务重启事件。
- 多进程共同监听、IPv4/IPv6 并存和同时存在的新旧实例均保留事实，不直接描述为“抢占”。
- 部分快照或失败不用于推导服务退出。中断后重新建立连续比较基线，不把跨间隔差异描述为确定时刻发生的事件。
- 进程和服务归属不明确时，展示原始端点及“归属待确认”，不合并为已确认的同一服务。
- 端口、Docker、Tunnel 数据具有各自观察时间；关联展示不得伪装成同一原子快照，也不据先后顺序直接推断因果。
- 使用时间窗口和事件数量双重上限；高频变化允许聚合，但保留“已聚合”说明。具体容量通过典型与高连接量样本验证确定。

### 5.3 验收标准

1. 详情能够回看指定端口的监听出现、消失、占用者及范围变化。
2. PID 复用、文件描述符变化、共同监听不会产生错误归因。
3. 查询失败、休眠恢复和暂停恢复显示中断，不伪造退出、重启或精确发生时间。
4. 时间线与聚合趋势共存，退出应用后会话历史清空，内存随持续刷新保持有界。

## 6. 优先能力三：端口对应的 Docker 状态

### 6.1 第一版信息

在已有端口到容器的唯一、可验证关联上补充：

- 容器名称、完整身份和发布端口映射。
- 生命周期状态，例如 running、restarting、exited。
- 已配置的健康检查结果，例如 starting、healthy、unhealthy。
- 启动时间、可读取的重启计数，以及本次会话观察到的启动代次变化。
- 采集时间、获取失败和信息过期状态。

没有健康检查时明确显示“未配置健康检查”，不能把 running 翻译为“应用健康”。Docker 的 HEALTHCHECK 是独立配置能力，见 [Dockerfile 官方说明](https://docs.docker.com/reference/dockerfile/#healthcheck)。

### 6.2 采集与操作约束

- 复用当前明确的本地 Docker socket 和命令执行封装，不跟随远程 context，不另加远程 Docker 管理功能。
- 扩展容器 inspect 的结构化解析；缺失、未知字段按能力不足处理，不导致端口查询失败。
- 已关注或当前选中的容器，在端口消失后仍保留有限的按 ID 查询能力，以便区别“容器退出”和“无法读取”。不扩展为全部停止容器列表。
- 容器删除或重建时保留原身份，提示重新关联；不自动把同名新容器当成原实例。
- 使用独立、可取消的低频状态采集及缓存，不阻塞本机端口快照更新，也不为列表每一行单独执行命令。
- 状态失败不清空已有端口事实，旧状态须注明过期，不能持续显示为当前健康。
- 延续现有停止容器前的 fresh 身份核验及结果验证，不增加自动停止或重启动作。

### 6.3 后续可选项

若真实排障案例仍需要资源上下文，再考虑在展开详情时读取 CPU/内存。Docker 已提供 stats 能力，见 [官方文档](https://docs.docker.com/reference/cli/docker/container/stats/)。本轮不实施全容器持续资源采样，也不把 CPU 100% 直接判定为应用故障。

### 6.4 验收标准

1. 能区分运行状态、健康检查结果和端口监听事实，三者独立呈现。
2. 未配置健康检查、daemon 不可用、容器删除、容器退出与信息过期均有明确状态。
3. 容器重启后能识别启动代次变化，并在时间线中显示观察证据。
4. 一个容器映射多个端口时共享采集结果；映射不唯一时不强行关联。
5. Docker 状态采集失败或超时不阻塞端口查询、搜索和已有安全操作流程。

## 7. 界面与架构接入

### 7.1 界面

- **主列表**：仅补充紧凑的偏差或容器状态标识，不新增大量资源列。
- **端口详情**：集中展示实际访问范围、用户预期、Docker/Tunnel 证据与最近事件。
- **局部拓扑**：只绘制可确认的映射与已观察连接，说明边的含义；不能把网络连接画成已验证业务依赖。
- **菜单栏**：展示活动偏差数量和快速跳转，避免持续闪烁；与主窗口共享结果，不独立采集。
- **设置**：管理关注策略及可选本地通知，不提供通用规则编辑器。

### 7.2 最小技术拆分

以下是建议职责与类型名，实施时根据现有结构调整，不为计划提前建设通用框架。

| 职责 | 建议接入方式 |
|---|---|
| 长期关注目标与预期 | 新增小型 `PortExpectation` 模型及本地配置存储，只保存用户设置 |
| 偏差计算 | 由独立 evaluator 比较事实和预期，输出正常、偏差、无法判断及证据 |
| 事件生成 | 新增 `PortEvent` 与有界会话事件存储，基于完整快照和明确中断状态计算 |
| Docker 状态 | 在现有服务归属边界内增加独立状态快照；不让视图直接执行命令 |
| 生命周期与派生状态 | 由 `PortViewModel` 管理任务和共享结果，页面 ViewModel 负责展示筛选 |

不强行把新逻辑全部写入已经承担刷新与安全操作的 `PortViewModel`。端口、Docker 和 Tunnel 状态分别保留更新时间、完整性与失效信息；展示缓存应依赖各自 revision，避免只有辅助状态变化时界面不更新。

## 8. 实施顺序与阶段出口

本节是本轮实施顺序，不复用历史 PRD 的 P0/P1 编号。三个功能分阶段交付，不要求同时上线。

| 阶段 | 交付物 | 进入下一阶段的条件 |
|---|---|---|
| 0：事实与身份边界 | 明确多端点比较、关注目标、采样中断及过期状态；确认 Cloudflare 接入基线 | 样例能够区分监听事实、转发映射、用户预期与未知状态 |
| 1：访问范围预期 | 设置、保存、删除关注策略；详情偏差说明；菜单栏摘要 | 无预期不高优先级告警；部分结果不误报恢复；IPv4/IPv6 和多监听端点覆盖 |
| 2：端口事件时间线 | 有界事件存储、端口详情时间线、采样中断说明 | PID 复用、共享监听及中断恢复场景验证通过 |
| 3：Docker 状态关联 | inspect 扩展、独立缓存、健康状态、启动代次事件 | 容器退出、删除、daemon 失联与不唯一映射均可正确降级 |
| 4：使用验证与收敛 | 用真实 Mac mini 开发服务案例验证解释、提示和刷新开销 | 能更快回答三个核心问题；若仍需资源上下文，再评估按需 CPU/内存 |

验证重点是偏差与事件的语义正确性，以及复用现有采集后的开销。新增测试覆盖身份、缺失数据、状态失效和跨采样比较等实质风险；UI 文案与低影响布局通过人工检查确认，不机械复制实现编写测试。

## 9. 完成标准与持续范围约束

本轮完成应满足：用户从一个端口进入详情，即可了解实际访问范围、与预期的偏差、最近关键变化及可确认的容器状态；需要停止进程或容器时，继续使用现有身份校验与确认流程。

成功信号包括：真实案例中能解释误改监听地址、服务占用者变化和容器重启；持续偏差不重复打扰；采样中断与数据缺失不被解释成正常或故障；新增采集不明显拖慢端口查询和交互。性能结论应通过实施前后相同负载下的测量给出，不预设未经验证的数值承诺。

后续每个候选功能均先回答：

1. 是否能帮助用户理解或处理一个具体端口的问题？
2. 能否在现有列表、详情和菜单栏内清楚表达？
3. 结论是否有足够数据支持，并能说明未知状态？
4. 是否引入需要长期维护的新监控对象、远程凭据或自动化执行环境？

优先完善已有诊断闭环。暂缓功能不作为本计划的隐含承诺，也不因预留模型或界面而提前实现。


## 10. 本轮实施范围（2026-11-06）

本轮按用户确认先实现以下三项能力。

- **端口事件时间线**。本次会话最近 30 分钟的 TCP 监听出现、消失、占用记录和地址集合变化，以及容器启动代次变化。首次完整采样建立基线，部分结果、失败、暂停、休眠或过长间隔中断比较。事件最多保留 1,000 条，达到上限时说明较早记录已移除。历史监听元数据最多保留 512 条，清除启动参数，消失记录可从列表上方入口按端口搜索和回看。
- **局部拓扑**。沿用已有连接流程图，补充 Tunnel 映射、Docker 宿主端口到容器端口映射，以及已观察到的 TCP 对端。独立展示映射观察时间，归属不唯一、手动连接器或过期映射使用候选关系表达。
- **Docker 状态**。选中唯一关联容器的详情时，每 15 秒通过已确认的本地 socket 按完整容器 ID 查询，缓存 10 秒。端口消失后选中详情仍可读取原容器。区分生命周期、健康检查、启动时间、重启计数、容器删除、读取失败和上次观察结果。切换到其他容器、清除选择或暂停时取消当前任务。

事件时间为采样观察时间。Docker 启动代次事件仅覆盖详情持续观察期间，短暂变化可能在采样间隔内遗漏。容器状态与端口快照独立采集，查询失败后重新建立容器比较基线。

验证覆盖文件描述符变化、PID 复用、共同监听、IPv6、多监听地址、部分结果、采样中断、有界存储、历史入口、Docker 状态解析、本地端点限制、缓存以及删除与不可读的区分。真实回环监听已用于验证局部拓扑和端口消失后的历史入口。Docker 真实容器状态仍需在可用本地 daemon 环境完成验证。
